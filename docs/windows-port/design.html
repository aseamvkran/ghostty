1. Executive Overview

Goal: Bring Ghostty to Windows as a first-class, GPU-accelerated, native terminal emulator that feels like it was built for Windows — not a Linux port with a Windows wrapper.

Key insight: Ghostty's architecture already separates platform-specific code (apprt) from the core terminal emulation (libghostty). The core is ~95% platform-independent. We only need to build the Windows "apprt" layer — the native windowing, input handling, and platform integration.

Current state: Significant Windows groundwork already exists in the codebase: ConPTY, Windows PTY, process spawning, font discovery, I/O threads, and build system scaffolding. An open PR (#12403) by @mattn provides a minimal Win32 skeleton that opens a window and runs cmd.exe.

2. Design Philosophy

Ghostty's Core Principles (applied to Windows)

  • Native: Use Win32 API directly. No Electron, no GTK-on-Windows, no XAML Islands. The terminal should feel like a Windows app — proper title bar, system menu, DPI awareness, Windows keyboard shortcuts (Ctrl+C for copy, etc.).
  • Fast: GPU-accelerated rendering via OpenGL (WGL). SIMD-optimized VT parsing. Multi-threaded architecture with dedicated read, write, and render threads.
  • Feature-rich: Tabs, splits, search, Kitty graphics protocol, Unicode, ligatures — everything the macOS and Linux versions support.
  • Shared core: Maximum code reuse with the existing Zig core. Only platform-specific code should be new.
Decision: We follow Ghostty's existing pattern — the Linux app uses GTK4 via Zig C API calls, so the Windows app will use Win32 API via Zig (with zigwin32 bindings). No C++, no C#, no managed languages. Pure Zig + Win32 C API.

4. Tech Stack Decisions

DecisionChoiceRationale
Language Zig Consistent with codebase. Zig compiles to native code, calls C APIs directly. The GTK app is also pure Zig calling C APIs.
Win32 Bindings zigwin32 Type-safe Zig bindings for Win32. Already adopted in PR #12403. Recommended by the Zig community. Future-proof as Zig 0.16 removes std.os.windows.
GPU API OpenGL 4.3+ via WGL Ghostty already has a complete OpenGL renderer. WGL is the standard way to use OpenGL on Windows. All modern GPUs support OpenGL 4.3+. No need for DirectX complexity.
PTY ConPTY Already fully implemented. Windows 10 1809+ required. ConPTY is the standard modern pseudo-console API.
Font Rendering FreeType Already implemented with Windows font directory scanner. Cross-platform consistency. DirectWrite could be added later for better ClearType.
Text Shaping HarfBuzz Already used across all platforms. Handles complex scripts and ligatures.
Why not C++? Rejected Would break the single-compilation-unit model. Zig can call all Win32 C APIs directly. C++ adds build complexity with no benefit.
Why not C#/WPF/WinUI? Rejected Requires .NET runtime dependency. Can't integrate with Zig build system. Not consistent with Ghostty's "no runtime dependency" philosophy.
Why not DirectX? Deferred OpenGL works well for terminal rendering. DirectX 12 would require rewriting the entire renderer. Could be a future optimization if needed.

6. Implementation Plan (5 Tiers)

Tier 1: Foundation — Basic Working Terminal In Progress (PR #12403)

Get a window that opens, creates a ConPTY, runs a shell, and displays output with GPU rendering.

  • Win32 window creation (RegisterClassExW, CreateWindowExW)
  • Win32 message loop (GetMessage, TranslateMessage, DispatchMessage)
  • WGL OpenGL context (ChoosePixelFormat, wglCreateContext)
  • CoreSurface initialization and wiring
  • SwapBuffers after drawFrame
  • WM_SIZE → sizeCallback for terminal resize

Result: Terminal window opens, cmd.exe runs, output is visible, window resizes work.

Tier 3: Window Management — DPI, Focus, Title Todo

DPI Awareness (PerMonitorV2)

The manifest already declares PerMonitorV2 DPI awareness. Implementation needed:

WM_DPICHANGED → {
    new_dpi = HIWORD(wParam);
    scale = new_dpi / 96.0;
    // Resize window to suggested rect
    SetWindowPos(hwnd, NULL, rect.left, rect.top, rect.right - rect.left, rect.bottom - rect.top, ...);
    // Update content scale
    CoreSurface.contentScaleCallback(scale, scale);
    // Rebuild font atlas at new scale
}
Multi-monitor: When dragging between monitors with different DPIs, WM_DPICHANGED fires. Must handle gracefully without flickering.

Tier 4: Advanced Features — Tabs, Splits, Menus Todo

Tab Bar

Options considered:

ApproachProsCons
Custom drawn tab bar Full control, consistent look, theme support More code to write, accessibility needs manual work
Win32 Tab Control (TCM_*) Native, accessible, familiar Ugly default style, limited customization
Custom HWND-based tabs Good control, proper focus handling Must handle all drawing
Decision: Custom drawn tab bar in the OpenGL surface, similar to how other modern Windows terminals handle it. This gives us full theming support and avoids the dated look of native tab controls.

Splits

Each split creates a new CoreSurface backed by its own ConPTY. The Win32 surface manages child surfaces and handles resize distribution. Splitter bars are custom-drawn with drag handling.

Context Menu

WM_RBUTTONUP → {
    menu = CreatePopupMenu();
    AppendMenuW(menu, MF_STRING, ID_COPY, L"Copy");
    AppendMenuW(menu, MF_STRING, ID_PASTE, L"Paste");
    AppendMenuW(menu, MF_SEPARATOR, 0, null);
    AppendMenuW(menu, MF_STRING, ID_SETTINGS, L"Settings");
    TrackPopupMenu(menu, TPM_RIGHTBUTTON, pt.x, pt.y, 0, hwnd, null);
}

Multiple Windows

Each window is an independent HWND with its own message processing. The App struct manages a list of windows. WM_WAKEUP is sent to all windows that need core tick processing.

7. GPU Rendering on Windows

OpenGL via WGL — How It Works

Ghostty's OpenGL renderer is already fully functional. On Windows, we just need to provide an OpenGL context via WGL (Windows OpenGL). The rendering code itself is 100% shared.

WGL Context Creation (from PR #12403)

1. GetDC(hwnd)                          // Get device context
2. ChoosePixelFormat(hdc, &pfd)          // Select pixel format (RGBA, 32-bit, double-buffered)
3. SetPixelFormat(hdc, format, &pfd)     // Apply pixel format
4. wglCreateContext(hdc)                 // Create OpenGL context
5. wglMakeCurrent(hdc, hglrc)            // Make context current on this thread

Thread Handoff (Critical!)

Main thread:
  1. Creates WGL context
  2. Calls wglMakeCurrent(null, null)     // Release from main thread
  
Render thread:
  1. Calls surface.makeContextCurrent()   // Acquire on render thread
  2. Loads GL functions via GLAD
  3. Runs render loop at ~120 FPS
  4. Calls SwapBuffers(hdc) after each frame
Note: OpenGL contexts can only be current on one thread at a time. The main thread must release the context before the render thread can acquire it. This is already handled in PR #12403's Surface.zig.

GLAD Function Loading on Windows

GLAD loads OpenGL functions via two mechanisms on Windows:

  • wglGetProcAddress() — For OpenGL 1.2+ extension functions
  • GetProcAddress(opengl32.dll) — For OpenGL 1.0/1.1 core functions

This is already handled by the existing GLAD loader when passed null as the loader function.

8. Windows Edge Cases & Pitfalls

Path Handling

IssueSolution
MAX_PATH (260 char) limitation Manifest declares longPathAware. Use \\?\ prefix for long paths. Registry key: HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled
Backslash vs forward slash Win32 APIs accept forward slashes. Normalize in display only. Zig's std.fs handles both.
Drive letters (C:\) Path operations must handle drive letter prefix. Don't strip it.
UNC paths (\\server\share) Support in path resolution. ConPTY working directory can be UNC.
Reserved filenames (CON, PRN, NUL) Don't create files with these names. Check in config path validation.

UTF-8 vs UTF-16

IssueSolution
Win32 APIs use UTF-16 (WCHAR) All Ghostty strings are UTF-8. Convert at the Win32 API boundary using std.unicode.utf8ToUtf16LeStringLiteral() or MultiByteToWideChar.
Clipboard data is UTF-16 Convert CF_UNICODETEXT to/from UTF-8 when reading/writing clipboard.
ConPTY output encoding ConPTY outputs UTF-8 by default (Windows 10 1903+). No conversion needed for terminal data.
File paths in config Config files are UTF-8. Convert paths to UTF-16 only when calling Win32 file APIs.

ConPTY Quirks

IssueSolution
ConPTY adds extra newlines Known issue in older Windows versions. Windows 11 23H2+ is much better. May need workarounds for older versions.
No SIGWINCH equivalent Use ResizePseudoConsole() directly. Already implemented in WindowsPty.setSize().
Process exit detection ReadFile returns 0 bytes / ERROR_BROKEN_PIPE when process exits. Already handled in threadMainWindows().
Ctrl+C handling ConPTY handles Ctrl+C → CTRL_C_EVENT automatically. Don't intercept WM_KEYDOWN for Ctrl+C when terminal is in raw mode.
Adjacent conpty.dll Can bundle conpty.dll for older Windows versions. Load via LoadLibrary with adjacent path.

DPI and Display

IssueSolution
Multiple monitors, different DPI PerMonitorV2 manifest. Handle WM_DPICHANGED. Rebuild font atlas on DPI change.
Fractional scaling (125%, 150%) Content scale = DPI / 96.0. Font size * scale. Pixel-perfect grid alignment.
Remote Desktop DPI RDP can change DPI mid-session. Handle WM_DPICHANGED even in RDP scenarios.

Other Windows-Specific Issues

IssueSolution
Windows Defender false positives Code-sign the executable. Submit to Microsoft for whitelisting.
Antivirus scanning delays Use MOVEFILE_DELAY_UNTIL_REBOOT for locked files. Handle ERROR_SHARING_VIOLATION.
UAC elevation Never require elevation. Detect elevated parent and warn.
Windows Terminal integration Ghostty can be added as a Windows Terminal profile (JSON settings fragment).
Dark/Light mode Read AppsUseLightTheme from registry. Listen for WM_SETTINGCHANGE.
Line endings (\r\n vs \n) Config files: accept both. Terminal output: ConPTY handles translation.

9. Test Strategy

Unit Tests (Zig test framework)

zig build test -Dtest-filter=<filter>
  • Path handling: backslashes, drive letters, UNC, long paths, reserved names
  • UTF-8 ↔ UTF-16 conversion at Win32 API boundaries
  • Keyboard VK → Ghostty key translation
  • DPI calculations and content scale
  • Clipboard data round-trip
  • Config file loading from %APPDATA%
  • ConPTY creation and resize
  • Window class registration

Integration Tests

  • Terminal output rendering correctness (vttest)
  • Keyboard input → terminal echo round-trip
  • Multi-monitor DPI switching
  • Window resize → terminal grid recalculation
  • Copy/paste with Unicode content
  • IME composition (CJK input)

Stress Tests

  • Large output throughput (cat large file)
  • Rapid resize events
  • Many concurrent terminals
  • Memory leak detection (no Valgrind on Windows — use UMDH or custom allocator tracking)
